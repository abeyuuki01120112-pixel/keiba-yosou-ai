（案B）が第一候補として承認されたことを受け、neutral閾値・複数走の集約方法・一貫性/分散の

## STEP2: neutral閾値A〜Dの実データ比較

| 案 | 幅 | \|delta\|以下でneutralになる件数/29件 |
|---|---|---:|
| A | ±0.5 | 2件（7%） |
| B | ±1.0 | 4件（14%） |
| C | ±1.5 | 6件（21%） |
| D | ±2.0 | 7件（24%） |

29件のうち、**22件（76%）は4案いずれの閾値でも分類が変わらない**（絶対値2.2以上）。
閾値選択が実際に効くのは、境界付近の7件（0.2, 0.3, 0.7, 0.8, 1.1, 1.4, 1.9）のみ。

閾値ごとの挙動:
- **A（±0.5）**: `2019105556 @ 中山turf2200`の2走（+0.7, +0.2）が両方とも「positive」に分類される。
  raceScoreは小数第1位までの複合スコア（memberLevel/timeGap/raceTime/final3F/weightの加重平均）
  であり、0.2〜0.7程度の差は各サブスコアの丸め・馬場補正の粒度から見て通常のブレの範囲内である
  可能性が高い。これを「positive」と断定するのは過大解釈のリスクがある。
- **B（±1.0）**: 上記の0.7/0.2ペアをneutralとして吸収する最小の閾値。`2021105898 @ 阪神turf2200`の
  -0.8もneutralになる。一方、1.1・1.4・1.9はまだpositive/negativeとして残る。
- **C（±1.5）**: Bに加えて1.1・1.4もneutralに吸収する。
- **D（±2.0）**: 1.9もneutralに吸収し、24%がneutralになる。実データの多くの真の信号
  （2022106120の+2.8〜+3.7等、CASE Dの実例）まで閾値に近づき、余裕が少なくなる。

### 推奨: 案B（±1.0）

感覚ではなく実データから、「明らかにノイズ水準（1点未満）の差」だけをneutralとして吸収し、
2022106120の実例（後述、+2.8〜+3.7の一貫したプラス）のような明確な信号を圧迫しない、最小限の
閾値として±1.0を推奨する。**ただし、29件・相関のある10グループという小さな母数からの推定であり、
確定的な閾値ではない。** 将来データが増えた際に再検証すべき値として記録する（STEP12参照）。

## STEP3: 複数走の集約方法A〜Dの比較

現在の実データはほぼ全て`sampleCount=2`（10グループ中9グループ）で、`sampleCount=3`は
1グループのみ（`2022106120 @ 中山turf2500`: +3.7, +2.8, +3.3）、`sampleCount>=4`は0件。

| 案 | n=2グループでの挙動 | n=3グループでの挙動（2022106120） |
|---|---|---|
| A: 単純平均 | 2値の算術平均（=中央値と数学的に同一） | mean = 3.27 |
| B: 中央値 | Aと完全に同一（n=2では平均=中央値） | median = 3.30（Aとほぼ同じ） |
| C: 直近重み付き平均 | 直近走の重みを増やすが、n=2では「新しい方に多少寄る」程度の違いしか生まない | 3走とも近い値（3.7/2.8/3.3）のため、重み付けしてもほぼ変化なし |
| D: 外れ値を弱めた平均（winsorized/trimmed） | **n=2では機能しない**（トリムすると片方のデータが丸ごと消えるか、trimする対象が無い） | n=3でも対称にトリムするには最低5点程度が望ましく、現状では実質機能しない |

| 観点 | A: 単純平均 | B: 中央値 | C: 直近重み付き | D: winsorized/trimmed |
|---|---|---|---|---|
| 少数サンプルへの強さ | ○（n=1でも定義可） | ○（n=1,2でAと同一） | △（重み設計が必要） | **×（n=2〜3では機能しない）** |
| 1走だけ極端な値が出た時の耐性 | 低い（`2021100913 @ 中京`の+14.4/+5.3のように、n=2では平均が外れ値に直接引っ張られる） | Aと同一（n=2では区別不能） | 低い（外れ値が直近走なら逆に強調される） | 高い（想定上）が**現在のデータ規模では発動しない** |
| 最近能力が変化した馬への追従 | 低い | 低い | **高い**（設計目的通り） | 低い |
| 説明可能性 | **最も高い**（「平均」で説明が完結） | 高い | 中（重み式の説明が要る） | 低い（トリム基準の説明が要る） |
| future leakage | なし（個々のdeltaが既にCHECKPOINT10.7で安全と確認済み。集約方法自体はleakageに影響しない） | なし | なし | なし |
| V1としての単純さ | **最も単純** | 単純 | やや複雑 | 複雑、かつ現状オーバースペック |

### 推奨: 案A（単純平均）

現在の実データの大半（10グループ中9グループ）が`sampleCount=2`であり、この条件下では
**単純平均と中央値は数学的に完全に同一の値になる**（`2022106120`のn=3グループでもmean=3.27・
median=3.30とほぼ差が無い）。したがって現時点で案AとBを区別する実益は無い。案C（直近重み付き）
は明確な設計目的（成長への追従）を持つが、それを裏付けるだけの複数走データ（n>=3、しかも
時間差のある値のばらつき）がまだ乏しい。案D（winsorized/trimmed）はn=2〜3では原理的に
機能しないため、現時点では時期尚早と判断する。

**単純平均を第一候補としつつ、n>=3が増えてきた段階で中央値への切り替え（外れ値耐性のため、
実装コストはほぼゼロ）を再検討する**、という段階的な方針を推奨する。

## STEP4: CASE C（成長誤認）の実データ検証

実データの中に、まさにCASE Cが懸念する状況の実例が見つかった。

```
igacchi（baseAbility=63.7）の全5走（時系列順）:
2025-10-20 中山turf1900  raceScore=60.1
2025-12-20 小倉turf1800  raceScore=58.7
2026-02-20 函館turf1900  raceScore=60.6
2026-04-20 中山turf2100  raceScore=65.5   ← 対象条件1回目
2026-06-20 中山turf2100  raceScore=73.4   ← 対象条件2回目
```

このケースでは、対象条件（中山turf2100）の2走（+5.7, +12.2のdelta）が、たまたま**キャリアの
一番新しい2走とも一致している**。全体のraceScoreの推移自体が60.1→58.7→60.6→65.5→73.4という
右肩上がりの傾向を示しており、この馬が単に成長期にあるだけで、中山turf2100自体に強い適性が
あるかどうかは、このデータだけからは判別できない。

一方、`zendanhayabusa`（deltas +1.9, +3.8、同じ中山turf2100条件）の全5走は
58.6→63.5→68.3→65.4→67.8と非単調（3走目で一度ピークをつけ、その後下がって再上昇）であり、
igacchiほど明確な成長誤認の懸念は無い。**同じ条件・似た時期の2頭でも、キャリア全体の推移次第で
「delta＝適性」と信じてよい度合いが変わる**ことを実データが示している。

また`2021100913 @ 中京turf2000`（deltas +14.4, +5.3）も、全8走を見ると
53.4→53.7→62.9→65.8→**73.4**→69.8→**70.4**→70.7という全体的な右肩上がりの中で、
最初の中京走（+14.4という最大級のdelta）が記録されている。案B自体（abilityBeforeRace比）は
career平均比（案A、CHECKPOINT10.7）よりこの手の誤認を軽減するが、完全には防げないことが
実データでも確認できた。

### growthWarningフラグ案（提示のみ・未実装）

以下のような設計を将来検討できる（今回は補正式・実装は行わない）。

- 対象条件の各走について、その走の直前nfil走（例: 直前5走）のraceScoreが単調増加に近いか
  （例: 順位相関や単純な傾き）を判定し、単調増加が強い場合に`growthWarning: true`を立てる。
- あるいは、対象条件の走が「キャリアのうち時期的に新しい側に偏っているか」（対象条件走の
  平均的な出走順位が、全体の出走順位の中央値より有意に新しいか）を見る、より単純な代替案もある。
- **いずれも今回は設計案の提示に留め、閾値・実装は行わない。**

## STEP5: CASE D（持続的小幅プラス）の実データ検証

実データの中に、CASE Dが想定する状況そのものの実例が見つかった。

```
2022106120 @ 中山turf2500: deltas = +3.7, +2.8, +3.3（2025-12-07, 2025-12-27, 2025-03-28）
mean=3.27, median=3.30, stdev=0.37, MAD=0.40, 符号一致率=100%
```

3走とも small〜moderate（+2.8〜+3.7）で、しかも分散が非常に小さい（stdev=0.37）。これは
「1回だけ+6」のような単発の大きな値よりも、**繰り返し観測された一貫した中規模のプラス**であり、
STEP5の問いに対する回答としては、**scoreの大きさ（aggregatedDelta）と一貫性（後述consistency）は
別々の指標として持つべき**という結論を支持する実例になっている。単純平均だけを見れば
「+3.27」という一つの数字にしかならないが、この馬のケースはconsistencyを併記することで
初めて「1回だけの+6」より信頼できる、という判断材料をユーザー・ChatGPTに提供できる。

## STEP6: CASE E（分散の大きいケース）の実データ検証

実データで最も顕著な2例:

```
2021100913 @ 中京turf2000: deltas = +14.4, +5.3
  → 符号は両方positiveで一致（signAgreement=100%）だが、stdev=4.55と非常に大きい。
    「常にプラスだが、プラスの大きさが安定しない」ケース。

2021105541 @ 京都turf2200: deltas = +5.2, -2.3
  → 符号自体が割れる（signAgreement=50%）。単純平均だけを見ると mean=+1.45で
    「軽くプラス」に見えるが、実際には1回はプラス・1回はマイナスであり、
    「適性が安定している」とは到底言えない。CASE Eが懸念する状況そのもの。
```

この2例は明確に異なる性質の「不安定さ」を示している。前者は方向は一致するが大きさが暴れる、
後者は方向自体が一致しない。**単一の平均値だけでは両者を区別できない**——STEP6・STEP7の
要請通り、confidence（データ量）とは別に、consistency（安定性）を分離して持つ必要がある
ことが実データからも裏付けられた。

## STEP7: consistency指標A〜Dの比較

上記5グループ全体で試算した結果:

| 馬×条件 | deltas | stdev | MAD | 符号一致率（±1.0閾値） |
|---|---|---:|---:|---:|
| 2019105556 @ 中山2200 | +0.7, +0.2 | 0.25 | 0.25 | n/a（両方neutral） |
| 2021100913 @ 阪神2200 | +0.3, +2.2 | 0.95 | 0.95 | 100% |
| 2021100913 @ 中京2000 | +14.4, +5.3 | 4.55 | 4.55 | 100% |
| 2021105541 @ 京都2200 | +5.2, -2.3 | 3.75 | 3.75 | **50%** |
| 2021105898 @ 阪神2200 | -2.4, -0.8 | 0.80 | 0.80 | 100% |
| 2022106120 @ 中山2500（n=3） | +3.7,+2.8,+3.3 | 0.37 | 0.40 | 100% |
| houohbiscuits @ 小倉1800 | +11.0, +7.7 | 1.65 | 1.65 | 100% |
| igacchi @ 中山2100 | +5.7, +12.2 | 3.25 | 3.25 | 100% |
| shakeyourheart @ 中京2000 | +5.2, +3.2 | 1.00 | 1.00 | 100% |
| zendanhayabusa @ 中山2100 | +1.9, +3.8 | 0.95 | 0.95 | 100% |

**n=2グループでは、stdev（案A）とMAD（案B）は数式上完全に一致する**（2点の中央値=平均、
中央絶対偏差=標準偏差になるため）。n=3の`2022106120`でもほぼ同じ値（0.37 vs 0.40）。したがって
現在のデータ規模ではAとBを区別する実益が無い（STEP3の平均/中央値と同じ構図）。

案C（符号一致率）は、`2021105541`（50%）とその他大半（100%）を明確に区別でき、
「方向自体が割れている」ことを最も直感的に伝えられる。一方で`2021100913 @ 中京`
（stdev=4.55だが符号一致率100%）のように、**符号一致率だけでは「同じ方向だが大きさが暴れる」
ケースを検出できない**という弱点も実データで確認された。

案D（raw値のまま、指標化しない）は最も安全だが、STEP6で見た通り「平均だけでは判断できない」
という問題への回答にはならない。

### 推奨: 案C（符号一致率）を第一候補、ただしAの限界を明記

理由:
1. 最も説明しやすい（「2走中1走だけプラス」を50%と表現でき、標準偏差の値がいくつなら
   「安定している」と言えるかという追加の較正が要らない）。
2. n=2でも意味のある値になる（stdev/MADのように「n=2では常に同じ値になり大小比較がしづらい」
   という問題が無い——符号一致率は0%/50%/100%という明確な区分を持つ）。
3. **ただし、大きさの暴れ（`2021100913 @ 中京`のようなケース）を見逃すという明確な弱点がある。**
   これは今回のV1では受容可能なトレードオフとして記録し、将来MAD等を併記する拡張の余地を
   残す（STEP12）。

## STEP8: 最終HorseEvidenceデータ構造案（設計のみ・コード未実装）

```typescript
// 設計イメージ（このラウンドでは実装しない）
interface HorseEvidenceEvaluation {
  sampleCount: number;                 // CHECKPOINT10.4のHorseEvidence.sampleCountをそのまま利用
  rawDeltas: number[];                 // 時系列順（古い→新しい）の各走のrawPerformanceDelta
  aggregatedDelta: number | null;      // 単純平均（STEP3推奨）。sampleCount=0ならnull
  evidenceDirection: "positive" | "neutral" | "negative" | "unknown"; // ±1.0（STEP2推奨・暫定）
  confidence: HorseEvidenceConfidence; // 既存（CHECKPOINT10.6、horseEvidenceConfidence.ts）
  consistency: {
    signAgreementRate: number | null;  // STEP7推奨（符号一致率）。sampleCount<2ならnull
  } | null;                            // sampleCount<2なら評価不能としてnull全体
}
```

例（2022106120 @ 中山turf2500、実データそのまま）:
```
sampleCount = 3
rawDeltas = [+3.7, +2.8, +3.3]
aggregatedDelta = +3.27
evidenceDirection = "positive"
confidence = "medium"          // CHECKPOINT10.6のB案: 3〜4走→medium
consistency = { signAgreementRate: 1.0 }
```

例（2021105541 @ 京都turf2200、実データそのまま——不安定な例）:
```
sampleCount = 2
rawDeltas = [+5.2, -2.3]
aggregatedDelta = +1.45
evidenceDirection = "positive"   // 平均だけを見ればpositiveと出てしまう
confidence = "low"               // sampleCount=2 → low
consistency = { signAgreementRate: 0.5 }  // ここでconsistencyの低さが可視化される
```

`confidence`（データ量の信頼度）と`consistency`（結果の安定性）が完全に独立したフィールドで
あり、上記2例目のように「aggregatedDeltaは正だが、consistencyが低い」という組み合わせを
型上・値の上で矛盾なく表現できることを確認した。
